### **Функциональные требования**

Верхнеуровневые Use Cases (основной поток). Источник: Task2/furps-table.md — F9, F13, +R7.

| **№** | **Действующие лица или системы** | **Use Case** | **Описание** |
| :-: | :- | :- | :- |
| UC-1 | Менеджер бэк-офиса депозитов; АБС; Deposit Service | Публикация актуальных ставок | 1. Менеджер ведёт ставки в модуле ставок АБС (вместо Excel). 2. При изменении ставок АБС вызывает callback Deposit Service. 3. Deposit Service обновляет кэш ставок. **Результат:** актуальные ставки опубликованы и готовы к раздаче потребителям. |
| UC-2 | Оператор кол-центра банка; Система кол-центра; Deposit Service | Просмотр ставок оператором кол-центра банка | 1. Оператор открывает карточку депозитов в системе кол-центра. 2. Система кол-центра запрашивает актуальные ставки у Deposit Service (Rates API). 3. Deposit Service возвращает ставки из кэша (< 300 мс). 4. Оператор консультирует клиента по актуальным ставкам. **Результат:** оператор видит актуальные ставки в реальном времени. |
| UC-3 | Оператор партнёрского кол-центра; Партнёрский кол-центр; SFTP-сервер; Deposit Service | Получение ставок партнёрским кол-центром | 1. Deposit Service (SFTP Export Job) ежедневно формирует файл с актуальными ставками (CSV). 2. Файл выкладывается на SFTP-сервер. 3. Внешняя система партнёрского кол-центра забирает файл по SFTP. 4. Оператор партнёра консультирует клиента по ставкам из файла. **Результат:** партнёрский кол-центр получает актуальные ставки без API-интеграции. |

### **Нефункциональные требования**

| **№** | **Требование** |
| :-: | :- |
| P2 | Ставки отдаются системе кол-центра за время < 300 мс — раздача из кэша Deposit Service, без обращения к АБС |
| P3 | Система кол-центра и ИБ не обращаются к АБС напрямую за ставками — источник для всех потребителей один: кэш Deposit Service |
| P4 | АБС масштабируется только вертикально — нагрузку от потребителей ставок берёт на себя Deposit Service |
| R1 | Rates API и SFTP Export Job доступны 24/7 на уровне 99,9% |
| +R7 | Передача ставок партнёрскому кол-центру — только через файловый обмен (SFTP); API-вызовы невозможны |
| +R1 | Передача файла партнёру выполняется по защищённому протоколу SFTP |
| +R3 | Технологии совместимы с существующими: Deposit Service — Java Spring Boot; интеграции с системой кол-центра (Java) — по REST |
| F10 | В кол-центр и партнёру передаются только депозитные ставки; данные кредитного бэк-офиса не раскрываются |

**Суть решения.**
Источник правды по ставкам — модуль ставок в АБС (заменяет Excel). Deposit Service выступает единой точкой раздачи ставок и предоставляет **два канала** для двух разных потребителей:

1. **Rates API (REST, синхронный)** — для системы кол-центра банка. Ставки кэшируются в Deposit Service и отдаются за миллисекунды. Кэш обновляется по callback от АБС при изменении ставок.
2. **SFTP Export Job (по расписанию)** — для партнёрского кол-центра. Раз в сутки формируется файл (CSV) и выкладывается на SFTP-сервер; внешняя система партнёра забирает его. Это единственный возможный канал — у партнёра нет API (+R7).

Решение опирается на принципы из Task3:
- **P2, P3, P4 (изоляция АБС).** Ни система кол-центра, ни ИБ не обращаются к АБС за ставками напрямую. Все читают из кэша Deposit Service. Перегруженная Oracle БД защищена от дополнительной нагрузки при росте числа звонков.
- **F10 (разграничение).** В кэш ставок и в файл попадают только депозитные ставки; данные кредитного бэк-офиса не раскрываются.
- **+R3 (совместимость).** Система кол-центра — Java Spring Boot, как и Deposit Service; интеграция по REST — естественна и не требует новых компетенций.

**Почему кэш, а не запрос в АБС на каждый звонок.** При маркетинговой кампании число звонков резко вырастет. Прямые запросы из системы кол-центра в АБС за ставками поставили бы под угрозу работоспособность АБС (P3/P4). Кэш в Deposit Service снимает эту нагрузку и обеспечивает отклик < 300 мс (P2).

### **Альтернативы**

| Альтернатива | Причина отклонения |
| :- | :- |
| Система кол-центра запрашивает ставки напрямую из АБС | Нарушает P3/P4: при росте звонков прямые запросы перегрузят Oracle БД и угрожают работоспособности банка |
| Партнёрский кол-центр получает ставки через API Deposit Service | Невозможно (+R7): партнёр работает во внешней системе, API-вызовы недоступны, только файловый обмен |
| Push-уведомление системе кол-центра при изменении ставки | Сложнее в реализации на MVP; система кол-центра не имеет готового endpoint для приёма; периодический pull из кэша достаточен |
| Отдельный микросервис только под ставки | Избыточно: Deposit Service уже владеет данными о ставках (кэш, callback от АБС); дублирование инфраструктуры не оправдано на MVP |
| Передача файла партнёру по email вместо SFTP | Менее надёжно и хуже автоматизируется; партнёр сам предложил SFTP как предпочтительный канал |
| Раздача ставок партнёру в реальном времени (чаще раза в сутки) | Не требуется бизнесом; суточная выгрузка покрывает потребность; снижает сложность и нагрузку |

**Недостатки, ограничения, риски**

- **Окно рассинхронизации (банк).** Между изменением ставки в АБС и обновлением кэша Deposit Service возможна задержка — оператор кратковременно увидит устаревшую ставку. Снижается коротким TTL кэша и надёжной доставкой callback.
- **Суточная задержка (партнёр).** Партнёрский кол-центр получает ставки раз в сутки — внутри дня данные могут устареть. Это принятое ограничение файлового обмена; при необходимости частоту выгрузки можно увеличить.
- **Надёжность callback от АБС.** Если АБС не доставит уведомление об изменении ставки, кэш устареет незаметно. Нужны контроль доставки, периодическая полная синхронизация (reconciliation) и алерты.
- **Согласование формата файла.** Формат CSV и состав полей нужно согласовать с партнёром заранее; изменения формата потребуют координации с внешней стороной.
- **Безопасность SFTP.** Файл со ставками выкладывается во внешний обмен — требуются управление ключами/доступом к SFTP и контроль, что в файл не попадают лишние данные (F10).
- **Зависимость от готовности модуля ставок в АБС.** UC-2 и UC-3 не заработают, пока команда АБС не реализует ведение ставок и callback — это критический путь дорожной карты.
