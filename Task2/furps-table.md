# FURPS+ таблица требований — банк «Стандарт», MVP онлайн-депозитов

| Код | Требования | Комментарий |
|-----|------------|-------------|
| F | **Функциональные (Functionality)** | |
| F1 | На сайте новый клиент видит список депозитов с актуальными ставками | Данные о ставках поступают из нового модуля ставок в АБС |
| F2 | Новый клиент может подать заявку на депозит на сайте (ФИО + телефон) | Заявка передаётся в систему кол-центра; менеджер звонит клиенту |
| F3 | Менеджер кол-центра видит заявку в своей системе; может предложить особые условия | Требует интеграции сайта с системой кол-центра |
| F4 | Новый клиент после звонка обязан прийти в отделение для очной идентификации | Регуляторное требование ЦБ РФ; онлайн-идентификация новых клиентов невозможна |
| F5 | В интернет-банке авторизованный клиент видит список депозитов с актуальными и персонализированными ставками | Персонализированные ставки рассчитываются на стороне бэка |
| F6 | Авторизованный клиент может подать заявку на открытие депозита в ИБ, указав счёт и сумму | Основной сценарий MVP |
| F7 | Заявка в ИБ подтверждается СМС-кодом | **АЗТ.** SMS-функционал реализуется командой банка без изменений ядра подрядчика (см. +R3) — влияет на архитектуру |
| F8 | На этапе MVP менеджер бэк-офиса депозитов вручную обрабатывает заявку и подтверждает условия депозита в АБС | MVP-ограничение; автоматическая обработка — цель Target-версии |
| F9 | Ставки по депозитам ведутся в АБС (новый модуль) и доступны сотрудникам бэк-офиса депозитов и бэк-офиса кредитов | **АЗТ.** Сейчас ставки ведутся только в Excel-файлах — это главный барьер для цифровизации |
| F10 | Бэк-офис депозитов и бэк-офис кредитов не имеют доступа к данным друг друга | **АЗТ.** Требование безопасности из текущего процесса; влияет на модель прав в АБС и новом сервисе |
| F11 | Клиент получает СМС-уведомление после подтверждения ставки менеджером бэк-офиса | Отправка через SMS-шлюз банка |
| F12 | Клиент получает СМС-уведомление после открытия депозита | Отправка через SMS-шлюз банка |
| F13 | Операторы кол-центра банка видят актуальные ставки депозитов в своей системе | **АЗТ.** Добавлено: необходимо для консультации клиентов; требует интеграции нового источника ставок с системой кол-центра |
| U | **Удобство использования (Usability)** | |
| U1 | Интерфейс работы с депозитами в ИБ и на сайте максимально удобен для клиента | UX-требование; детализируется на этапе дизайна |
| U2 | Все клиентские интерфейсы (ИБ, сайт) соответствуют принятой в компании дизайн-системе: цвета, шрифты, брендированные элементы | Единый брендинг обязателен для всех клиентских каналов |
| R | **Надёжность (Reliability)** | |
| R1 | Все сервисы (ИБ, новый сервис обработки депозитов) работают 24/7 и доступны в 99,9% случаев | **АЗТ.** SLA 99,9% ≈ не более 8,7 ч простоя в год; требует отказоустойчивой архитектуры |
| R2 | При сбое в основном ЦОД сервисы ИБ переключаются на резервный ЦОД | **АЗТ.** Требует развёртывания ИБ и нового сервиса в двух ЦОД |
| R3 | ИБ поддерживает горизонтальное масштабирование: равномерное распределение запросов между серверами и ЦОД | **АЗТ.** Требует stateless-дизайна ИБ; критично при росте аудитории после запуска онлайн-депозитов |
| P | **Производительность (Performance)** | |
| P1 | Отклик по всем операциям в ИБ — миллисекунды; целевое значение не более 300 мс | **АЗТ.** Текущая проблема: некоторые операции занимают более 1 сек |
| P2 | Справочные данные (в том числе ставки) загружаются не дольше 300 мс | **АЗТ.** Требует кэширования ставок; нельзя запрашивать их напрямую из АБС при каждом открытии страницы |
| P3 | В новом процессе интернет-банк не работает напрямую с API или БД АБС | **АЗТ.** БД АБС уже перегружена; онлайн-заявки создадут дополнительную нагрузку; необходим промежуточный сервис-буфер между ИБ и АБС |
| P4 | АБС масштабируется только вертикально (ограничение Oracle БД) | **АЗТ.** Ограничение подтверждает необходимость изоляции АБС от прямой нагрузки со стороны ИБ |
| S | **Поддерживаемость (Supportability)** | |
| S1 | Для всех новых API разрабатывается документация, достаточная для дальнейшего расширения системы | OpenAPI / Swagger спецификация для нового сервиса |
| S2 | Все операции подачи и обработки заявок логируются | Добавлено: критично для банковской системы; позволяет расследовать инциденты и проводить аудит |
| S3 | Архитектура решения допускает добавление новых продуктов (кредиты, накопительные счета) без кардинального переписывания | Добавлено: MVP — первый шаг; следующий этап — кредиты онлайн |
| +R | **Ограничения (Restrictions)** | |
| +R1 | Передача данных на сайте и в ИБ защищается шифрованием: TLS/HTTPS | **АЗТ.** На сайте передаются персональные данные (ФИО, телефон); в ИБ — финансовые данные клиента |
| +R2 | SMS-функционал реализуется командой банка без изменений ядра платформы ИБ | **АЗТ.** Изменения ядра требуют участия и оплаты подрядчика; SMS-логику необходимо вынести во внешний компонент |
| +R3 | При разработке использовать технологии банка (MS SQL, Oracle) или совместимые с существующими платформами (.NET, Java, PL-SQL, PHP) | **АЗТ.** Ограничивает выбор стека нового сервиса; приоритет — Java (есть экспертиза в команде АБС) |
| +R4 | Новые технологии должны быть понятны сотрудникам банка: желательно наличие внутренней экспертизы хотя бы на уровне языков программирования | Снижает риск зависимости от внешних подрядчиков |
| +R5 | Текущая версия платформы ИБ (.NET Framework 4.5) несовместима с Kafka — на MVP Kafka не использовать; рассматривать как опцию после обновления платформы | **АЗТ.** Прямое ограничение на выбор интеграционного паттерна: между ИБ и новым сервисом нужен REST или иной совместимый механизм |
| +R6 | На перспективу рассмотреть перевод депозитного модуля ИБ на микросервисную архитектуру | Не обязательно для MVP; учесть при проектировании для упрощения будущей миграции |
| +R7 | Передача данных в партнёрский кол-центр возможна только через файловый обмен (SFTP); API-интеграция недоступна | **АЗТ.** Добавлено: партнёрский КЦ — внешняя система без API; новый сервис должен содержать компонент выгрузки ставок в файл |
