### **Нефункциональные требования**

Архитектурно значимые требования (источник: Task2/furps-table.md, раздел АЗТ).

| **№** | **Требование** |
| :-: | :- |
| R1 | Доступность сервисов (ИБ, Deposit Service) 24/7 на уровне 99,9% |
| R2 | Failover интернет-банка на резервный ЦОД при сбое основного |
| R3 | Горизонтальное масштабирование ИБ между серверами и ЦОД |
| P1 | Отклик операций в ИБ — не более 300 мс |
| P2 | Справочные данные (ставки) загружаются не дольше 300 мс — кэширование на стороне Deposit Service |
| P3 | Интернет-банк не обращается напрямую к API/БД АБС — промежуточный сервис изолирует перегруженную Oracle БД |
| P4 | АБС масштабируется только вертикально (ограничение Oracle) — нагрузку берёт на себя Deposit Service |
| +R1 | TLS/HTTPS для всех внешних взаимодействий (сайт, ИБ) |
| +R2 | SMS-функционал реализуется командой банка без изменений ядра подрядчика ИБ |
| +R3 | Совместимость технологий: MS SQL, Oracle, .NET, Java, PL-SQL; приоритет — стек с внутренней экспертизой |
| +R5 | Текущая версия ИБ (.NET Framework 4.5) несовместима с Kafka — на MVP использовать REST |
| F10 | Разграничение доступа: бэк-офис депозитов и кредитов не видят данные друг друга |

**Суть решения.**
Вводится новый микросервис **Deposit Service** (Java Spring Boot) — асинхронный посредник между интернет-банком и АБС. Он решает ключевые архитектурно значимые требования:

- **P3, P4 (изоляция АБС).** Интернет-банк не обращается к АБС напрямую. Deposit Service принимает заявки, буферизует их и передаёт в АБС асинхронно. Перегруженная Oracle БД защищена от пиковой нагрузки со стороны онлайн-канала.
- **+R2 (SMS без ядра подрядчика).** Логика отправки SMS-кодов и уведомлений вынесена в Deposit Service (компонент SMS Component) и реализуется командой банка. Ядро монолита ИБ, принадлежащее подрядчику, не меняется.
- **+R5, +R3 (совместимость, Kafka).** Между ИБ (.NET Framework 4.5) и Deposit Service используется синхронный REST API — Kafka на MVP неприменима. Deposit Service пишется на Java Spring Boot, так как в команде АБС уже есть Java-экспертиза (та же платформа, что у системы кол-центра).
- **P2 (быстрые ставки).** Deposit Service кэширует ставки в собственной БД (Deposit DB) и обновляет их по callback от АБС. Клиент и кол-центр получают ставки из кэша за миллисекунды, без обращения к АБС.
- **F9, F10 (ведение и разграничение ставок).** Новый модуль ставок реализуется в АБС (PL-SQL, Deposit Rates Module) с ролевым доступом — депозиты и кредиты не видят данные друг друга.
- **R1, R2, R3 (доступность, failover, масштабирование).** Интернет-банк и Deposit Service развёртываются в обоих ЦОД, за балансировщиком, с горизонтальным масштабированием и переключением на резервный ЦОД.

### **Альтернативы**

| Альтернатива | Причина отклонения |
| :- | :- |
| Прямой синхронный вызов ИБ → API/БД АБС | Нарушает P3, P4: Oracle БД перегружена, пиковая нагрузка от онлайн-канала угрожает работоспособности банка и SLA 99,9% |
| Kafka между ИБ и Deposit Service | Нарушает +R5: текущая версия ИБ (.NET Framework 4.5) несовместима с Kafka |
| Реализация SMS-логики в ядре ИБ | Нарушает +R2: ядро принадлежит подрядчику, изменения требуют его участия и затрат |
| Ведение ставок в отдельной БД вне АБС | Нарушает F9/F10: АБС — система учёта и источник правды; разграничение доступа уже строится вокруг АБС; рассинхронизация данных |
| Расширение монолита ИБ депозитным функционалом без отдельного сервиса | Не решает P3 (нагрузка на АБС) и +R2 (SMS); ограничивает масштабирование, привязано к подрядчику |
| Deposit Service на .NET (как ИБ) | Допустимо по +R3, но Java-экспертиза в команде АБС сильнее, а сервис тесно интегрируется именно с АБС; выбран Java Spring Boot |

**Недостатки, ограничения, риски**

- **Новый сервис в эксплуатации.** Deposit Service требует отдельной поддержки: CI/CD, мониторинг, дежурство, инфраструктура в двух ЦОД. Растут операционные расходы на MVP-этапе.
- **Сложность асинхронной интеграции.** Обмен Deposit Service ↔ АБС асинхронный — усложняется отладка, нужна обработка ошибок, повторов и идемпотентности при передаче заявок.
- **Окно рассинхронизации ставок.** Между изменением ставки в АБС и обновлением кэша в Deposit Service возможна задержка — клиент или оператор кратковременно увидят устаревшую ставку. Требуется ограничение TTL кэша и явная фиксация ставки при подтверждении заявки бэк-офисом.
- **Ручная обработка на MVP (F8).** Заявки по-прежнему обрабатываются бэк-офисом вручную — узкое место по скорости и масштабу. Это сознательное ограничение MVP; снимается в Target-версии (автоматическое открытие депозита).
- **Зависимость от ресурса команды АБС.** Deposit Service (Java) и модуль ставок (PL-SQL) разрабатывает преимущественно команда АБС — конкуренция за ресурс с текущими задачами сопровождения АБС.
- **Технический долг ИБ.** Монолит ИБ на .NET Framework 4.5 остаётся ограничением (нет Kafka, тяжёлое масштабирование). Перевод депозитного модуля на микросервисы (+R6) отложен на будущее — долг сохраняется.
